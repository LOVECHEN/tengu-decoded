# 研究总览与证据分级

## 范围

本轮核验以 Claude Code 2.1.300 Linux x86-64 提取物为主，辅以仓库已有的结构化清单和专题报告。
目标是回答三个不同问题：

1. 客户端实际能收集、保存或外发哪些信号？
2. 客户端实际实现了哪些账号状态与拒绝路径？
3. 社交平台上所谓“积分表”的具体权重，能否从客户端语料中复现？

## 证据分级

| 级别 | 含义 | 示例 |
|---|---|---|
| **A：直接证据** | 提取源码实现了该字段、端点、状态或分支 | `account_on_hold`、`device_id`、`billing_path` |
| **B：可观测信号** | 客户端会保存或发送信号，但没有证据证明它被用于风控打分 | 平台、订阅时间、模型、会话与设备注册 |
| **C：服务端可能** | 服务端天然能知道，但客户端语料无法证明其策略用途或权重 | 源 IP 声誉、支付卡类型、邮箱域名、同时登录策略 |
| **D：未发现或误命中** | 已搜索相关关键词和调用点，未找到对应逻辑，或命中只是随机字符串 | `risk_score`、虚拟卡减分、Linux 减分、KYC 打分 |

## 判定原则

- **能传输不等于已用于风控。** 例如 `platform` 出现在遥测 schema，只能证明服务端可以看到平台，不能证明 Linux 被扣分。
- **存在拒绝状态不等于存在客户端积分算法。** `account_on_hold` 是确认的 API 结果，但触发规则和阈值在服务端。
- **静态存在不等于运行时可达。** 功能开关、provider plane、账号类型和发布配置都会改变实际路径。
- **未在客户端找到不等于服务端不存在。** 本报告对服务端内部风控只能标为不可见，不做否定性推断。

## 可复现搜索结果

在 2.1.300 语料中，`risk_score`、`riskScore`、`trust_score`、`trustScore`、
`virtual_card`、`identity_verification` 均无对应实现命中。`kyc` 唯一命中来自机器生成字符串
`Hy0W3kYc6J`，不是 KYC 字段或逻辑。`banned` 的少量命中也是词库和物理 schema 中的 `BANNED_AGENT`，
不是账号封禁分支。
