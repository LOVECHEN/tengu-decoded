# 账号风控检测点核验

核验对象：[make_claude 的 X 帖](https://x.com/make_claude/status/2115501814090969583?s=46)。
由于 X 直连页面可读性不稳定，同时使用[teapawt 镜像转录](https://xitter.cf/aiamblichus)校对帖子全文。

## 核心结论

所核验的 X 帖将 Claude 账号风控描述为一套有明确加减分和阈值的积分系统。
在 Claude Code 2.1.300 客户端语料中，**未发现任何这样的分数字段、权重表、阈值、观察期状态机或本地裁决器**。

但这不表示帖子里的所有“原始信号”都是虚构的。客户端确实会提供账号创建时间、订阅时间、计划层级、
计费路径、平台、入口、安装 ID、账号/organization/session ID、模型与使用量等信息。
它们的“可观测性”有直接证据，但与账号封禁之间的因果关系和具体权重都不在客户端中。

## 确认存在的账号状态链

1. OAuth 或 API 响应可返回 `verification_required`、`billing_error`、`account_on_hold` 等状态。
2. OAuth refresh 遇到 `account_on_hold` 时会缓存该结果，并记录 `tengu_oauth_refresh_token_account_on_hold`。
3. 客户端将 `account_on_hold` 视为 blocked 结果，停止正常 Claude Code 使用路径。
4. 终端显示“Your account is on hold and can't use Claude Code”，并引导到 `https://claude.ai/restricted` 查看或申诉。
5. 另有 `organization_on_hold`、`organization_disabled`、`refused_ip_allowlist` 等组织或网络策略结果，不应与个人账号积分混为一谈。

因此，**“账号会被 hold”有 A 级直接证据；“由客户端上的分数阈值触发”没有证据**。

## 逐项检测点总结

| 类别 | 帖子中的说法 | 级别 | 客户端证据 | 核验结论 |
|---|---|---|---|---|
| 注册 | 干净 IP 是最重要加分项 | C | 服务端必然看到连接源 IP；客户端无 IP 声誉评分器 | 无法从本语料验证“最重要”和权重 |
| 注册 | Gmail 不优，其他邮箱服务商加分 | C/D | GrowthBook 属性可包含 email，但无域名分类或权重 | 邮箱可见不等于服务商打分 |
| 注册 | 注册即 KYC 会减分 | D | `kyc` 唯一命中是机器生成 ID 的子串 | 未发现 KYC 字段、状态或打分逻辑 |
| 注册 | 移动端注册加分 | C/D | 本语料为 Linux CLI，能上报 client/platform，不含移动注册风控 | 无直接证据 |
| 支付 | 注册后立即订阅或直接 Max 减分 | B/C | Profile 包含 `accountCreatedAt`、`subscriptionCreatedAt`、`subscriptionType` | 时序可计算，但未发现扣分权重 |
| 支付 | 支付 KYC 表示进入观察 | C/D | 存在通用 `verification_required`，但没有与支付 KYC 或 observation 相关的本地状态机 | 不能由通用验证错误推导出该说法 |
| 支付 | 外卡/Google Play 加分，虚拟卡减分 | B/C/D | 存在 `stripe/ apple/ google_play/ other` 计费路径，无实体/虚拟卡标记 | 只证实计费渠道可见，未证实加减分 |
| 使用 | 频繁跑空用量会减分 | B | 用量、限额、reset 和 extra usage 状态存在 | 用量可观测，未发现封禁分数关系 |
| 使用 | Desktop/Mobile 加分，Web 不加 | B/C | `platform`、`client_type`、`entrypoint` 可进入遥测 | 渠道可识别，无加分逻辑 |
| 使用 | 开启 Memory、记忆文件多加分 | B/D | Memory 是真实功能，其访问和事件可观测 | 未发现记忆数量对账号信任的权重 |
| IP/设备 | 稳定 IP 加分，经常变 IP 减分 | C | 服务端可按请求观察 IP，但客户端无该统计 | 可能是服务端信号，本语料不能给出权重 |
| IP/设备 | 代理必须全局/TUN | C/D | 客户端支持代理环境变量，但无 TUN 风控检测 | 这是网络路由建议，不是已证实打分点 |
| IP/设备 | 多设备登录减分 | B/C | 存在设备 ID、trusted devices、remote devices 与每账号设备密钥 | 服务端能建立设备集，但未发现“多设备=减分” |
| IP/设备 | 频繁登录、高并发减分 | B/C | 会话、OAuth refresh、auth health 和并行 session 可观测 | 可观测不能证明风控权重 |
| 账龄 | 账号越老分数越高 | B/C | 存在 `accountCreatedAt` 和 `tenure_bucket` | 账龄真实参与限额 reset/offer 规则，但未证实参与封禁分 |
| 平台 | Windows/macOS 不变，Linux 减分 | B/D | `platform` 会上报；语料没有 OS 信任权重表 | 平台可见，Linux 减分未证实 |
| 语言/时区 | 时区和中文无影响 | B/D | locale/timezone 可在不同功能路径中出现，无风控评分 | 客户端不足以证实“有”或“无”影响 |
| 模型 | 大量使用 Fable 减分 | B/D | 模型路由与使用事件可观测，Fable 是真实模型家族 | 未发现 Fable 特定风控逻辑 |
| 订阅 | 升级 Max 后进入观察期 | B/C/D | 计划迁移可见，但无 observation-period 状态 | 未发现可复现状态机 |
| 拒绝 | 接近阈值会掉登录，继续扣分即封禁 | A/D | `account_on_hold` 会阻断刷新和使用，并引导申诉 | hold 路径已证实；分数阈值、高分容忍度与递减过程未证实 |

## 实际可检测的信号族

### 账号与订阅

- `accountUuid`、`organizationUuid`、`organizationRole`。
- `subscriptionType`、`rateLimitTier`、`accountCreatedAt`、`subscriptionCreatedAt`。
- `tier`、`tenure_bucket`、`billing_path`、`billing_period`、`extra_usage_state`。
- 这些字段中，`tenure_bucket` 和 `billing_path` 确实参与服务端下发的 limit-reset/offer 资格判定，但不能推广为封禁评分。

### 设备与会话

- 持久安装 ID：`userID`、`machineID`、`summonSidKey`、`remoteControlMachineId`。
- 每账号 ECDSA P-256 设备密钥，以及 trusted-device/remote-device 注册。
- `session_id`、`parent_session_id`、`entrypoint`、`client_type`、`platform`、`appVersion`。
- 上述机制允许服务端把多个请求、会话和设备关联起来，但客户端不包含关联后的风控裁决。

### 使用行为

- 模型选择、计划限额、使用量状态、extra usage、功能暴露和 GrowthBook experiment。
- Memory、remote session、bridge、plugin、工具调用等功能均有可观测的事件或属性。
- 这些数据适合产品分析、限额与实验分流，是否被另一套服务端风控复用，本语料不可见。

## 最终判定

该 X 帖更像将经验规则、个案观察和真实存在的可观测信号，统一包装成了一套确定的“积分系统”。
客户端证据可以证明很多输入维度的可观测性，也可以证明 `account_on_hold` 这个结果状态；
但无法证明任何具体加减分、权重、阈值或观察期算法。
