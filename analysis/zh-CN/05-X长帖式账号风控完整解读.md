# Claude Code 账号风控：X 长帖式完整解读

> 核验对象：[make_claude 的 X 帖](https://x.com/make_claude/status/2115501814090969583?s=46)
>
> 样本范围：Claude Code 2.1.300 Linux x86-64 提取物，以及本仓库对应版本的 telemetry、device、API 和 plan-tier 报告。

这篇文档不只回答“帖子说得对不对”，而是把客户端里真正存在的身份、设备、订阅、遥测、OAuth 和账号阻断链逐层展开。

核心区别只有一句话：

> **客户端能观察某个信号，不等于已经证明服务端用这个信号给账号加减分。**

---

## 01｜先给最终结论

X 帖把 Claude 账号风控描述成一套明确的积分制：注册方式、IP、邮箱、付款渠道、设备、使用习惯、模型和账龄分别加减分，分数低到阈值后掉登录或封禁。

对 2.1.300 客户端语料做静态核验后，可以得到四个结论：

1. **账号被阻断是真实功能。** 客户端明确处理 `account_on_hold`，会停止正常使用并引导到申诉页。
2. **大量原始信号确实可见。** 安装 ID、账号 UUID、组织 UUID、会话 ID、订阅层级、账龄、计费路径、平台、入口和用量状态都会在不同链路中出现。
3. **设备关联能力是真实存在的。** 客户端有持久安装标识、trusted device、remote device、每账号 P-256 设备密钥和会话绑定证明。
4. **客户端没有出现帖子描述的积分算法。** 未发现 `risk_score`、`trust_score`、权重表、封禁阈值、分数衰减器或“观察期”状态机。

因此，最准确的表述不是“帖子全假”，也不是“积分表已被逆向确认”，而是：

> 帖子混合了真实可观测信号、用户经验归纳和无法从客户端验证的服务端策略，并把它们包装成了一套确定的积分公式。

---

## 02｜证据应该怎么读

本文把证据分成四级：

| 级别 | 含义 | 例子 |
|---|---|---|
| A：客户端直接证据 | 能找到函数、字段、端点或状态分支 | `account_on_hold`、`device_id`、`billing_path` |
| B：信号可观测 | 客户端会生成、保存或外发，但用途不一定是风控 | 平台、会话、订阅时间、模型、设备注册 |
| C：服务端可能知道 | 网络或业务层天然可见，客户端看不到服务端如何使用 | 源 IP、支付卡属性、并发设备集合 |
| D：当前未发现 | 已搜索客户端语料但没有对应实现 | 本地积分、虚拟卡扣分、Linux 扣分、KYC 分值 |

后文每个检测点都会回答四个问题：

- 客户端具体看到了什么？
- 数据经过哪些函数和端点？
- 这条链在产品中的直接用途是什么？
- 能否据此推出封禁加减分？

---

## 03｜客户端里没有“本地封号积分器”

对 2.1.300 语料搜索以下典型命名，没有找到对应实现：

```text
risk_score
riskScore
trust_score
trustScore
virtual_card
identity_verification
observation_period
```

`kyc` 的唯一文本命中只是机器生成标识符中的随机子串，不是 KYC 字段。`banned` 的少量命中属于词库或物理 schema 中的 `BANNED_AGENT`，不是账号封禁状态机。

这意味着客户端中没有发现类似下面的逻辑：

```text
score += clean_ip ? 20 : -30
score += google_play ? 10 : 0
score -= linux ? 15 : 0
if score < threshold: ban(account)
```

但这个结论只限定于客户端：**服务端策略、特征工程、权重和阈值并不随 CLI 下发，因此客户端语料不能证明服务端没有风险模型。**

## 04｜真正存在的账号阻断链

客户端明确认识这些账号或策略结果：

```text
account_on_hold
verification_required
billing_error
organization_on_hold
organization_disabled
refused_ip_allowlist
```

其中 `account_on_hold` 的完整客户端链如下：

```text
服务端策略
  ├─ OAuth refresh 返回错误
  └─ 普通 API 直接返回 account_on_hold
          ↓
      $Pr(error) 分类
          ↓
 ui.set(refreshToken) 缓存 hold token
          ↓
 tengu_oauth_refresh_token_account_on_hold 事件
          ↓
 blocked mapper → state: "blocked"
          ↓
 O0o() / C6n() 构建终端提示
          ↓
 https://claude.ai/restricted
```

各步骤的直接用途：

| 调用关系 | 传递内容 | 功能用途 |
|---|---|---|
| 服务端策略 → OAuth refresh | token error | 把服务端账号裁决传回客户端；内部特征与阈值不可见 |
| OAuth refresh → `$Pr(error)` | 原始错误 | 区分 hold、`invalid_grant` 和瞬时刷新失败 |
| `$Pr(error)` → `ui.set()` | refresh token | 缓存已命中 hold 的 token，避免持续重试刷新 |
| hold cache → hold event | 账号状态 | 记录客户端走到了账号暂停分支 |
| `account_on_hold` → blocked mapper | auth reason | 把 API 错误归一化成统一 blocked 状态 |
| `account_on_hold` → `O0o()/C6n()` | 状态类型 | 显示专门的“账号已暂停”文案 |
| hold UI → restricted URL | 申诉入口 | 给用户提供查看原因和申诉的下一步路径 |

能够证明的结论：账号 hold、客户端阻断和申诉链都真实存在。

不能证明的结论：hold 由多少分触发、阈值是多少、哪些字段贡献多少权重。

## 05｜第一组关联：安装身份如何贯穿多个系统

### 5.1 `_M()`：安装级 `userID`

`_M()` / `getOrCreateUserID` 位于 `cli.beauty.js:115569`，生成或读取一个 64 位十六进制随机值。它不是硬盘序列号、MAC 地址或 CPU ID，而是按安装持久化的随机标识。

这个值会进入多条链：

```text
_M() userID
  ├─ ek.coreUserData.deviceId
  ├─ EBe().metadata.user_id.device_id → Messages API
  ├─ PW().user_id → /event_logging/v2/batch
  ├─ Mxo().device_id → GrowthBook exposure
  ├─ nT().id/deviceID → GrowthBook remote eval
  ├─ CDt().user.id → OTel collector
  └─ getUserBucket() → Datadog bucket 0–29
```

这些关联的用途分别是：请求归因、跨会话事件聚合、实验分组、遥测资源关联和错误采样。

风控含义：服务端在数据模型上可以把同一安装的多个请求和会话关联起来。

证据边界：没有客户端逻辑表示“一个 userID 登录多个账号扣多少分”。

### 5.2 `Umt()`：截断使用的 `machineID`

`Umt()` / `getOrCreateMachineID` 位于 `cli.beauty.js:115581`，同样生成 64 位十六进制随机值。

当前确认的外发形式是：

```text
Umt().slice(0, 12) → host_name_redacted → Datadog error report
```

用途是辅助错误报告聚类，不是把完整 machineID 发送出去。

### 5.3 `rPo()`：只用于 HMAC 的 `summonSidKey`

`rPo()` 位于 `cli.beauty.js:115596`。密钥本身不外发，客户端只计算：

```text
sid = HMAC-SHA256(summonSidKey, sessionId + artifactSlug)[0:16]
```

随后：

```text
rPo() + q() sessionId
  → Se() 生成 sid
  → Bns() 构建 relay-bound POST
  → /api/frame/comments/{slug}/{thread}/summon-status
```

用途是把状态上报绑定到具体会话和 artifact，同时不直接暴露本地密钥。

### 5.4 `f7s() → xO()`：远程控制主机标识

`remoteControlMachineId` 是一个持久 UUID，位于 `cli.beauty.js:115613`。它会原样进入：

```text
remoteControlMachineId
  → bridge payload.machine_id
  → POST /v1/environments/bridge
```

用途是注册或维持远程控制环境与当前主机的绑定。

它比 `machineID` 更直接地承担远程控制设备标识功能，但仍没有客户端加减分逻辑。

## 06｜第二组关联：账号、组织和会话如何进入请求

中心身份包 `ek.coreUserData` 位于 `cli.beauty.js:133593`，它把多个来源合并：

```text
_M()                  → deviceId
q()                   → sessionId
VC() / An()           → accountUuid / organizationUuid
profile cache         → subscriptionType / rateLimitTier
runtime               → platform / clientType / entrypoint / appVersion
```

中心身份包随后被多个消费者复用：

| 消费者 | 主要字段 | 直接用途 |
|---|---|---|
| `PW()` 一方事件 | `user_id`、账号、组织、会话、平台 | 标准化行为与诊断事件 |
| `nT()` GrowthBook 属性 | 设备、账号、组织、订阅、入口 | 远程特性评估和实验分配 |
| `CDt()` OTel resource | `user.id`、账号、组织、会话 | 关联日志、指标和 trace |
| `EBe()` Messages metadata | 设备、账号、会话、父会话 | 给模型请求附加归因元数据 |

这解释了为什么“平台、订阅、账号、设备和会话”可以同时出现在服务端数据里：它们不是五个互不相关的检测器，而是由共享身份包向不同传输管线分发。

## 07｜第三组关联：设备注册不是简单的“硬件指纹”

2.1.300 除了安装 ID，还引入了每账号 ECDSA P-256 设备密钥。

```text
每账号 P-256 keypair
  ├─ public_key
  │    → POST /api/organizations/:orgUUID/cowork/remote_devices
  │    → 服务端返回 deviceUUID
  │
  ├─ bind_attestation
  │    → POST /v1/code/sessions/{id}/device
  │    → 将 session 绑定到 target_device_id
  │
  └─ device_attestation
       → sin()
       → 给部分 session payload 签名
```

这套设计的直接用途是：

- 让服务端登记某账号下的远程设备公钥。
- 让会话绑定请求证明自己持有对应私钥。
- 让部分 session 事件带上设备签名。
- 降低伪造设备或伪造绑定的可能性。

同时还有传统 trusted-device 注册：

```text
account bearer + display_name
  → POST /api/auth/trusted_devices
  → device_token + device_id
```

因此，“多设备可被服务端观察”是合理且有结构证据的；“第二台设备固定扣多少分”仍没有客户端证据。

## 08｜IP 与代理：服务端可见，但客户端没有 IP 评分器

原帖最强调的通常是 IP 纯净度、稳定性、代理质量和 TUN 模式。

客户端证据分成三层：

| 层次 | 已确认事实 | 不能推出的结论 |
|---|---|---|
| 网络层 | 服务端天然看到每个连接的源 IP | 无法从客户端知道 IP 声誉库和权重 |
| 客户端层 | 支持 HTTP/HTTPS 代理环境变量和网络配置 | 没有发现“必须 TUN”检测器 |
| 策略结果层 | 存在 `refused_ip_allowlist` 等网络拒绝原因 | 不能等同于个人账号风险积分 |

IP 变化频率、ASN、数据中心代理、住宅代理、地理跳变都可能是服务端可计算信号，但这些计算不在 CLI 中。

所以更严谨的判定是：

> **IP 是天然可观测的服务端信号；帖子给出的具体加分优先级、扣分值和 TUN 规则无法由客户端验证。**

## 09｜邮箱、KYC 与验证：不要把三个概念混成一个

### 邮箱

GrowthBook 或 OTel 的部分路径可以包含 email，服务端账号系统本身也必然知道登录邮箱。

但是客户端没有发现：

```text
gmail.com → 低权重
outlook.com → 高权重
企业邮箱 → 固定加分
临时邮箱 → 固定扣分
```

邮箱可见不等于邮箱服务商评分表已被逆向确认。

### KYC

客户端没有找到可识别的 KYC 字段、KYC 分数或 KYC 观察期状态机。

### `verification_required`

客户端确实有通用 `verification_required` API 状态，但它只说明服务端要求附加验证。它不能自动等同于支付 KYC，也不能证明“注册时验证反而扣分”。

## 10｜订阅、支付和账龄：字段真实，封禁权重未知

OAuth profile 通过 `NPr()` 获取并缓存，典型字段包括：

```text
accountCreatedAt
subscriptionCreatedAt
subscriptionType
rateLimitTier
billingType
organizationType
```

随后形成几条明确用途链：

```text
NPr() profile fetch
  → Mn() profile cache
  ├─ Rr() 读取 subscriptionType
  ├─ VYs() 识别 billingType
  ├─ VC()/An() 提供 account/org
  └─ accountCreatedAt / subscriptionCreatedAt
```

在限额 reset/offer 规则中还能看到：

```text
tier
tenure_bucket: under_14 | 14-29 | 30-89 | 90-364 | 365+
billing_path: stripe | apple | google_play | other
billing_period
extra_usage_state
```

这些字段会进入：

```text
eligibility schema
  → POST /api/organizations/{org}/reset_rate_limits
```

这能证明：账龄、订阅层级和计费路径确实用于至少一部分产品资格或限额规则。

这不能证明：

- 新账号立即订阅必然扣分。
- 直接购买 Max 必然进入封禁观察期。
- Google Play 必然加分。
- Stripe 实体卡必然加分。
- 虚拟卡必然扣分。

尤其是“实体卡/虚拟卡”分类在当前客户端字段中并不存在；客户端看到的是计费路径，不是完整卡片风控属性。

## 11｜使用量、模型和 Memory：都可观测，但没有封禁公式

### 使用量

客户端能读取或记录计划限额、使用量状态、extra usage、reset 和功能使用事件。

直接用途包括：

- 展示用量和限额。
- 触发产品资格或 reset claim。
- 分析功能使用和错误。
- 进行实验分流。

没有发现“经常把额度用空固定扣分”的本地规则。

### 模型

模型选择和路由是可观测的，Fable 等模型家族也真实存在。但没有发现 Fable 专用风险分支或扣分权重。

### Memory

Memory 是真实功能，其启用、访问和相关行为可能进入产品事件。没有发现“记忆文件越多信任分越高”的实现。

这里最容易出现的推理错误是：

```text
事件中存在某字段
    ≠
该字段被风控系统消费
    ≠
该字段有固定分值
```

## 12｜平台、客户端入口和 Linux

客户端可以上报：

```text
platform
client_type
entrypoint
appVersion
sessionOrigin
```

这些字段的直接用途包括版本分析、平台兼容性、实验分组、错误定位和产品入口统计。

当前没有发现：

```text
Windows = 0
macOS = 0
Linux = -N
Desktop = +N
Mobile = +N
Web = 0
```

因此，平台和入口“可识别”是 B 级证据；Linux 扣分或移动端加分是 D 级未发现规则。

## 13｜会话、并发和频繁登录

客户端有完善的会话关联字段：

```text
session_id
parent_session_id
account_uuid
organization_uuid
device_id
target_device_id
```

它们允许服务端构建类似这样的关系：

```text
账号
  ├─ 安装 A
  │    ├─ session 1
  │    └─ session 2
  ├─ 安装 B
  │    └─ session 3
  └─ trusted / remote device registry
```

OAuth refresh、auth health、并行 session 和设备绑定也都有可观测点。

所以“服务端具备识别并发登录、多设备和频繁刷新的数据基础”是合理结论。

但当前不能从客户端推出：

- 同时两台设备是否一定扣分。
- 多少并发达到阈值。
- 切换账号是否进入观察期。
- 频繁刷新 token 的具体处罚权重。

## 14｜59 条调用关系可以压缩成 8 条主链

交互图中共有 48 个节点、59 条调用/传播边。为了便于顺读，可以压缩成以下八条主链。

### 主链 A：模型请求身份归因

```text
_M() + VC()/An() + q() + QC()
  → EBe().metadata.user_id
  → Messages API
```

用途：把模型请求关联到安装、账号、组织、当前会话和父会话。

### 主链 B：一方事件上传

```text
ek.coreUserData + _M()
  → PW() event row
  → /event_logging/v2/batch
```

用途：统一生成行为、诊断和实验事件，并批量上传。

### 主链 C：GrowthBook 特性评估

```text
ek.coreUserData
  → nT() attributes
  → /api/eval/{clientKey}
  → feature value / experiment variation
```

用途：基于账号、订阅、设备和入口等属性进行远程功能分流。

### 主链 D：实验曝光记录

```text
userID + account/org + session
  → Mxo() exposure
  → PW() event row
  → event batch
```

用途：记录哪个安装、账号或会话看到了哪个实验变体。

### 主链 E：设备登记与会话绑定

```text
P-256 device key
  → remote_devices registry
  → deviceUUID
  → /v1/code/sessions/{id}/device
  → bind_attestation
```

用途：登记设备公钥，并证明会话绑定请求持有对应私钥。

### 主链 F：远程 bridge

```text
remoteControlMachineId
  → bridge payload.machine_id
  → /v1/environments/bridge
```

用途：稳定标识远程控制主机和 bridge 环境。

### 主链 G：订阅与限额资格

```text
OAuth profile cache
  → tier + billing_path + tenure_bucket
  → eligibility schema
  → /reset_rate_limits
```

用途：按订阅、计费渠道和账龄判断产品资格或申请限额重置。

### 主链 H：账号 hold

```text
server policy result
  → OAuth/API error
  → $Pr(error)
  → hold cache + event
  → blocked state
  → hold UI
  → restricted / appeal
```

用途：让服务端账号裁决在客户端稳定地阻断使用并提供申诉入口。

## 15｜逐项核验速查表

| X 帖中的主张 | 客户端真实证据 | 判定 |
|---|---|---|
| 干净、稳定 IP 是核心加分项 | 服务端看到源 IP；客户端存在网络拒绝状态 | 信号可能存在，权重不可见 |
| Gmail 低分、其他邮箱高分 | 邮箱在账号系统和部分遥测路径可见 | 未发现域名评分表 |
| 注册 KYC 会扣分 | 无 KYC 字段或状态机 | 未发现 |
| 移动端注册加分 | 平台和入口可识别 | 未发现加分规则 |
| 注册后立即订阅扣分 | 账号与订阅时间都存在 | 时序可计算，扣分未证实 |
| Max 升级后进入观察期 | 订阅迁移可见 | 未发现观察期状态机 |
| Google Play 加分 | `billing_path` 可区分 Google Play | 渠道可见，加分未证实 |
| 虚拟卡扣分 | 客户端没有实体/虚拟卡字段 | 未发现 |
| 用空额度扣分 | 用量和限额状态可见 | 未发现封禁分关系 |
| Desktop/Mobile 加分 | `platform/client_type/entrypoint` 可见 | 未发现加分规则 |
| Memory 多会加分 | Memory 功能及事件存在 | 未发现数量权重 |
| 多设备登录扣分 | 设备注册、设备密钥和会话绑定存在 | 设备集合可见，扣分未证实 |
| 高频登录和并发扣分 | session、refresh 和 auth health 可见 | 阈值与权重不可见 |
| 账号越老分数越高 | `accountCreatedAt`、`tenure_bucket` 存在 | 账龄用于部分资格规则，封禁分未证实 |
| Linux 扣分 | `platform` 可见 | 未发现 OS 权重表 |
| 大量使用 Fable 扣分 | 模型选择可见 | 未发现 Fable 风控逻辑 |
| 接近阈值会掉登录，继续扣分会封禁 | `account_on_hold` 会阻断 refresh 和使用 | hold 已证实，分数过程未证实 |

## 16｜哪些是客户端永远回答不了的

即使把 2.1.300 客户端完全反编译，也不能仅靠客户端回答以下问题：

- 服务端是否有统一风险分，还是多个独立分类器。
- 某个 IP、ASN、国家或代理类型的具体权重。
- 支付卡 BIN、拒付历史、账单地址和设备之间如何关联。
- 多设备、并发会话和 token refresh 的阈值。
- 风险状态是否随时间衰减。
- 人工复核、自动分类器和申诉结果如何组合。
- `account_on_hold` 是否总由同一套策略产生。

客户端能看到的是输入字段的一部分和最终错误状态，而不是中间的服务端决策过程。

更接近真实系统的抽象应该是：

```text
客户端信号 ─┐
网络信号 ───┤
账号历史 ───┤
支付与订阅 ─┤→ 服务端策略/分类器 → 允许 / 验证 / 计费错误 / hold / 组织拒绝
使用行为 ───┤
设备关系 ───┘
```

这里的“服务端策略/分类器”是黑箱。客户端证据只覆盖左侧部分输入和右侧结果。

## 17｜真正值得记住的检测点

如果只保留可证实内容，Claude Code 客户端暴露或使用的关键检测维度是：

| 维度 | 具体标识或字段 | 直接用途 |
|---|---|---|
| 安装身份 | `userID`、`machineID`、`remoteControlMachineId` | 请求归因、错误聚类、远程主机注册 |
| 账号身份 | `accountUuid`、`organizationUuid`、role | 账号/组织归属和权限上下文 |
| 会话关系 | `session_id`、`parent_session_id` | 会话聚合与派生关系 |
| 设备身份 | P-256 key、deviceUUID、trusted-device token | 设备登记、签名和会话绑定 |
| 订阅 | `subscriptionType`、`rateLimitTier` | 功能门控、限额和实验属性 |
| 账龄 | `accountCreatedAt`、`subscriptionCreatedAt`、`tenure_bucket` | cohort 和部分资格规则 |
| 计费 | `billingType`、`billing_path`、`billing_period` | 计费路径归类和资格判断 |
| 客户端环境 | `platform`、`client_type`、`entrypoint`、version | 产品分析、兼容性、实验与诊断 |
| 使用行为 | 模型、用量、extra usage、功能事件 | 用量展示、产品分析和实验 |
| 结果状态 | hold、verification、billing、org/IP refusal | 客户端阻断与后续处理 |

最重要的边界是：

> **这是一张“服务端可能拥有的数据能力地图”，不是一张已经还原的封禁积分表。**

## 最终结语

X 帖最有价值的地方，是提醒用户不要把账号风控只理解为单一 IP 检测。Claude Code 客户端确实把安装、账号、组织、设备、会话、订阅、计费路径、平台和行为事件连接成了一个复杂的数据图。

但“数据图存在”和“积分公式已知”是两件不同的事。

现有证据能够完整还原客户端如何生成标识、如何传递字段、如何注册设备、如何上传事件、如何处理账号 hold；无法还原服务端究竟使用了哪些特征、各自权重多少、何时触发人工或自动裁决。

所以，对这类社交平台风控清单，最可靠的阅读方式是：

```text
先确认字段是否存在
再确认字段是否外发
再确认字段的直接产品用途
最后才讨论它是否可能被风控复用
```

跳过中间三步，直接给每个行为标注具体分值，就已经超出了当前客户端证据能够支持的范围。
